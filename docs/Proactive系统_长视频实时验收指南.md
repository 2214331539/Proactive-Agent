# Proactive 系统 · 长视频实时验收指南

> 版本：2026-11-08　|　代码：`D:\AScience\proactive-agent`　|　配套：《Proactive系统说明_主动性定义标准与系统框架》、`proactive_video_3d_v3.html`
> 验收目标：系统在开源长视频（M3-Bench robot）上**按真实时间**运行，人来核验它的主动行为是否合理。

---

## 1. 这次建了什么

系统主路径已经从“需求触发 → 决策模型直接给提醒 / 等待”换成说明文档里的“机会 → 价值 → 门控”：

```
视频帧 + 字幕 ─► 感知 VLM ─► FastState（世界）
                              ├─ C6 UserView     每个人以为的世界（认知差）
                              ├─ C7 GoalFilter   每个人要不要出门、到哪一步（截止风险 H）
                              └─ C8 Receptivity  对象本人在不在说话、赶不赶时间（打扰代价、q）
                                        │
C9 机会发现：① 用户请求（含“N 分钟后提醒我”）② 风险模板 ③ 认知差 ⑤ 目标推断 / 在找东西 ⑥ 风险预测 ✦ 开放发现
                                        │
C10 价值估计：模型只回答概率（p_cond、q），损失 / 有效率 / 代价查表 → 每种说法的 U，以及等待价值 V
C11 价值门控：U* ≤ 0 沉默；U* ≤ V + 0.1 再等等；否则用价值最高的方式（提示音 / 询问 / 提醒）开口
                                        │
C12 口语化草稿（机会变热时预生成）─► C13 频率与负担 ─► 豆包语音（预合成）─► 界面
C17 决策日志：每次决定（含沉默、等待）的全部中间量　　C18 评测：人工核验 + 标注窗口
```

| 组件 | 代码 |
|---|---|
| C6 / C7 / C8 | `pa/state/userview.py`、`goals.py`、`receptivity.py` |
| C9 | `pa/opportunity/`（`generators.py` 六类来源，`llm.py` 开放发现与概率模型） |
| C10 / C11 | `pa/value/estimator.py`，代价表 `pa/value/costs.yaml` |
| C13 | `pa/policy/burden.py` |
| 编排 | `pa/proactive/core.py` |
| C17 / C18 | `pa/storage/decision_log.py`、`pa/eval/opportunities.py`（命令 `pa eval`） |
| 语音 | `pa/output/tts.py`（豆包） |
| 界面 | `pa/ui/`（`pa ui`） |

## 2. 怎么验收

### 2.1 启动

```powershell
cd D:\AScience\proactive-agent
.venv\Scripts\python -m pa ui          # 浏览器打开 http://127.0.0.1:8765
```

1. 左上选视频源。推荐先用 **living_room_06 全片 · 16 分钟**，也可以选“🎬 自定义”：任选已下载视频、起点（mm:ss）、时长（分钟）。
2. 倍速选 1×（实时），右上角语音选“豆包语音”。
3. 点 **▶ 实时运行**。系统和视频同步按真实时间推进。中途刷新页面会自动接回正在运行的会话。

### 2.2 看什么

| 位置 | 内容 |
|---|---|
| 画面左下角“AI 正在掂量的机会” | 当前开口价值最高的机会：三种说法的价值条、橙色虚线是等待价值、此刻的决定 |
| 时间轴 | ◆ 记住请求　◇ 发现机会　橙点 再等等　绿点 提醒　蓝点 询问　青点 提示音；竖线是标注事件，红色虚线是截止 |
| 右上“主动消息” | “记住了…”“再等等…”以及每条主动消息：说了什么、依据哪个机会、p / q / H / U / V |
| “机会”页 | 每个机会的 p 的因子分解（如 会出门 0.97 × 出门时会忘 0.6 × 模型估计 0.72）、q 的理由、截止阶段、价值条 |
| “人物”页 / 底部条 | 每个人的出门概率与阶段、是否在说话 / 赶时间；认知差 |
| “决策”页 | 每个机会的决定每次变化都记一条，包括为什么沉默 |

### 2.3 怎么核验

| 操作 | 含义 | 计分 |
|---|---|---|
| ✓ 有用 | 这句话在这个时刻说是对的 | +L − 打扰代价 |
| ✗ 没必要 | 说的事是真的，但不值得打扰 | − 打扰代价 |
| ⚠ 判断错误 | 说的事是错的 | − 打扰代价 − 误报代价 |
| ⚑ 标记漏报 | 该说却没说（在那个时刻点） | 计入“完美助理” |

运行结束后，用“⟲ 回放核验”继续标。“▶ 看前后”会跳到消息前 15 秒。核验结果保存在 `runs/<run>/verdicts.jsonl`，可以随时改。

### 2.4 指标

```powershell
.venv\Scripts\python -m pa eval runs\<run>
```

| 指标 | 含义 | 期望 |
|---|---|---|
| PG_human | 人工核验口径：NPV ÷ 完美助理 NPV | > 0（0 = 从不说话，1 = 完美，< 0 = 添乱） |
| 有用率 | 有用 ÷ 已核验 | 越高越好 |
| 语音 / 小时、误报 / 小时 | 打扰频率 | 越低越好 |
| 标注口径 PG / 命中 / 提前量 | 按 `data/annotations/<video>.json` 的有效窗口结算 | 命中且提前量 > 0 |

最终版本：

| 运行 | 时长 | 主动消息 | 说了什么、何时 | 标注口径 |
|---|---|---|---|---|
| living_room_06 全片（`runs/ui_lr06_full_20261108_221704`） | 16 分钟 | 1 条语音 | 14:39.5“Sophie、Lily，快点，出门别忘了带伞，好像要下雨。”；前 14 分钟（瑜伽、聊天、约晚饭、叮嘱开会）全部沉默或等待 | PG 1.0，FAH 0，比截止早 13.1 s |
| living_room_02 25:00 起（`runs/accept/living_room_02_1500s_20261108_222416`） | 6 分钟 | 1 条语音 | 26:29 记住“三分钟后提醒我泡面好了”，之后一直“再等等（还没到约定时间）”；29:28 “Jack，三分钟到啦，方便面好啦，快去看看。” | PG 1.0，FAH 0 |

迭代过程（每一轮都是在真实长视频上发现问题、修掉、再跑）：

| 运行 | 主动消息 | 标注口径 | 暴露的问题 → 修复 |
|---|---|---|---|
| lr06 全片 v1 | 11（语音 2） | 命中，PG 0.26 | 没有时机条件的请求（开会、晚饭）刚说完就响提示音；开放发现猜“柜门开着” → 无时机请求只记住；开放发现收紧 |
| lr06 全片 v2 | 11（语音 4） | 命中，PG −0.56 | 一部手机在几个人手里传，被当成“忘带 / 认知差” → 别人手里的东西不算落下；认知差只看地点间移动 |
| lr06 全片 v3 | 2（语音 1） | 命中，PG 0.96，提前 6.9 s | 瑜伽时一帧 leaving 标签把全屋判成“走向门口” → “走向门口”需跨来源佐证 |
| lr06 全片 v4 | 3（语音 2） | 晚 18 s，PG −0.45 | 提示音已用完，门控仍选提示音，语音提醒被耽误 → 门控只在可用方式里选 |
| lr02 片段 v2 | 2（语音 2） | 准点，PG 0.64 | 称呼错人（Lisa）→ 用字幕里的说话人名字 |
| lr02 片段 v3–v5 | 4 → 1 → 2 | 未命中 → 命中 | 含糊的“Wait for three minutes”吞掉明确的提醒请求；开放发现把“水壶烫”按安全类 100 分计 → 合并保留明确的那句、机会按需求 ID；开放发现打五折、封顶 8 分、每 10 分钟最多一次 |

要注意：每个配置只跑了 1–2 次。决策模型对同一机会的概率估计会波动（实测同一时刻 0.35–0.72），所以同一配置重跑，提醒时刻可能前后差十几秒。要下结论，应在多个视频上各跑多次，看分布。

## 5. 语音（豆包）

- 当前 Key 只开通了 **seed-audio**（生成式音频，`/api/v3/tts/create`），单句 13–25 s，偶尔超过 60 s。
  所以系统在机会“变热”（再等等、或价值接近 0 且截止临近）时就预生成草稿并合成语音。实测雨伞提醒发出时，音频已经就绪。
- 在火山引擎控制台为该 Key 开通“豆包语音合成 2.0”后，把 `config/deepseek.yaml` 中的 `tts.api` 改成 `tts2`、`tts.voice` 填音色（如 `zh_female_xiaohe_uranus_bigtts`），即可走流式接口，首包约 1 s。
- 语音没合成好时，界面先响提示音、显示文字，音频到了再播。

## 6. 已知局限

- **样本少：** 目前只在 2 个视频上调过参。第 3 节里的 bedroom_09、office_02 等还没跑，换视频很可能暴露新问题。
- **身份不稳：** 第一人称视频里同一个人常被识别成多个实体。系统靠字幕说话人名字和“全屋聚合”兜底，所以“对谁说”偶尔会错。
- **开放发现精度低：** LLM 提出的候选多是推测，现在用打折、封顶、限频压住，等于大部分时候不用它。要真正做到“系统自己发现需求”（L3），下一步应优先做认知差（③）和预期违背（④）的结构化来源。
- **语音慢：** 当前 Key 的 seed-audio 单句 13–25 s，预合成没赶上时语音会晚于文字。开通 TTS 2.0 后可以解决。
- **代价表是人为设定的：** `costs.yaml` 里的损失、有效率、打扰代价都是第一版假设，需要用人工核验结果来校准。决策日志（`value_decisions` 表）已经记下了每次判断的全部中间量。
- **未做感知质量评测：** 状态补丁本身的准确率没有单独评测。主动性表现受 VLM 动作标签质量影响很大。
